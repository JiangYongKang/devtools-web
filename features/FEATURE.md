### 文档目的

本文件是本仓库前端在编码、测试、文档与任务管理上的统一规范与总入口：约定目录分工、TASK/DOC 模板、交付与验收口径，并维护任务列表索引与状态。

仓库中的交付物包含两大类，适用同一套规范：每一项均须有独立的 TASK_XXX.md 与 DOC_XXX.md 闭环，不因是否调用后端 HTTP 而省略文档或验收。

1. 面向使用者的开发者工具界面（页面、路由或可嵌入的交互面板）  
   例如：用户在浏览器中粘贴 JSON，前端完成格式化/压缩展示，或调用后端 API 后再展示结果；HTTP 客户端、WebSocket 调试等强依赖浏览器能力的工具。侧重交互清晰、反馈可预期、错误可诊断、可访问性与性能可接受。

2. 面向站内需复用的前端基础能力（组件、组合式逻辑、纯函数工具、请求封装等）  
   例如：工具页通用布局、剪贴板/下载辅助、主题与本地偏好、统一的加载与错误提示、与后端无关的纯展示或校验逻辑。侧重可复用、可测试、与路由/页面解耦；未必单独作为一级导航功能推广，但在多工具间共享时同样按任务编号管理。

任务列表同时收录工具型页面/流程与基建类前端条目；最终形态是独立页面、嵌套面板或仅被其他模块导入，以对应 TASK_XXX.md 为准。

架构共识：上述条目在实现层一律视为相互独立的功能单元（可按「工具页 / 特性模块 / 纯模块」划分，命名与目录与仓库约定一致），例如「时间戳转换页」与「通用请求封装」在架构层级上无高低之分。是否发起网络请求、是否依赖后端不由任务类型决定，而由该功能是否声明需要 API 客户端层 约束：仅在需要访问后端时在统一出口发起调用；可在浏览器本地完成的逻辑应保持可离线或弱依赖。

### 产品与工程定位

本项目承载网站前端的可复用工程能力集合：无论是带路由的开发者工具页面，还是以模块形式在站内复用的组件与逻辑，均应可用、可维护、可验证，拒绝散落的一次性拷贝粘贴。

- 代码质量：结构清晰、边界与错误路径可预期；关键交互与数据来源有据可查（与注释规范一致）。
- 体验与一致性：文案、错误提示、空状态与快捷键/焦点习惯应与站内既有模式对齐；可复用模块应有稳定用法与必要时可运行的演示或说明。
- 可测试性：适合单测的逻辑须可用项目脚本运行测试；依赖浏览器 API、网络或真实后端的能力须在 DOC 中写明验证步骤与结论。
- 文档闭环：每个编号任务必须有对应的 TASK（要什么）与 DOC（如何实现、如何接入、如何验收）。

### 架构约定（功能模块与路由/页面）

- 功能独立：每个编号任务对应的能力应封装为清晰边界的模块或页面单元（分包、目录与命名与仓库约定一致），可单独覆盖测试；不因是否注册路由而拆薄或合并核心业务交互。
- 后端依赖可选：同一套前端逻辑既可纯浏览器计算，也可在需要时经由统一的 HTTP/WebSocket 客户端调用后端；是否在 UI 上暴露「调用服务端」路径，不应导致两套互拷的业务实现。
- 变更隔离：新增、下线或调整对外请求契约时，优先调整 API 封装层与类型/契约说明，避免仅为是否走后端而在页面内复制粘贴请求代码。

### 目录约定

| 路径                 | 用途                                                                 |
| -------------------- | -------------------------------------------------------------------- |
| features/FEATURE_FRONTEND.md | 本文件：前端总规范与任务列表索引、状态                       |
| features/TASK_XXX.md | 单项任务的需求与验收说明（不写实现细节），三位数字编号与任务列表一致 |
| docs/DOC_XXX.md      | 与 TASK 同编号的实现与使用文档（模块/数据流、用法、验证结果、限制） |

说明：TASK 描述要达成什么；DOC 描述如何实现与如何验证。实现细节禁止写在 FEATURE 的任务条目长文中，应落在对应 DOC_XXX.md。

### 任务文档规范（features/TASK_XXX.md）

- 命名：TASK_001.md、TASK_002.md … 使用三位数字，与 FEATURE 中任务编号一一对应，不得复用或错位。
- 粒度：每个编号对应一个主任务文件；子任务在同一文件内分节即可。
- 写法：以业务与可验收结果为导向；少写实现指令（不点名具体组件名、Hook 名、文件路径），把实现空间留给研发。
- 篇幅：各章节默认采用要点列举（每条尽量简短、可执行）；避免复杂表格与多层嵌套排版。
- Markdown：TASK 正文以简洁可读为先，少用装饰性语法（大量加粗、行内代码框、多级嵌套列表等）；必要的章节标题与编号列举即可。

### 编码与注释规范（全局）

- 语言与风格：与仓库现有技术栈（如 Vite、React）、目录结构与命名保持一致；改动范围限定在完成当前任务所需的最小集合。
- 注释：新增或修改的代码宜附简洁中文注释，说明非显而易见的业务含义、边界条件与设计取舍；避免复述代码字面含义的无用注释。
- 错误与用户反馈：用户可见的错误信息应清晰、可操作（必要时说明原因或下一步）；需注意将不可信文本以安全方式展示（避免将用户输入未经处理直接写入 `dangerouslySetInnerHTML` 等）。

### 运行环境与前端工程约定

- 构建与本地开发：以仓库根目录 `package.json` 中的脚本与依赖为准（当前为基于 Vite 的 React 应用）；Node 版本与包管理器（如 npm/pnpm）若团队有统一要求，以实现层 README 或 CI 配置为准并在 DOC 中引用。
- 语法与运行时：优先使用现行 ECMAScript 能力与 React 推荐的写法；在可读、可维护的前提下采用适合当前场景的异步、模块化与类型手段（若仓库逐步引入 TypeScript，新代码与迁移策略在对应 DOC 中说明）。
- 浏览器目标：以项目构建目标（如 `browserslist` 或 Vite 默认目标）为准；若某功能依赖较新的 Web API，须在 TASK/DOC 中写明兼容策略与降级方案。

### 测试与验收规范

- 自动化：以 `package.json` 中提供的测试脚本为准（若尚未接入测试框架，新增任务应在 TASK 中声明是否引入以及最低覆盖点）；纯逻辑与回归场景应补充或更新对应测试文件；提交前确保相关测试通过。
- 单测文件拆分：在逻辑体量与维护性允许的前提下，宜将同一任务域内的测试按主题拆分（例如成功路径与边界、错误与非法输入、网络或浏览器 API 的模拟等），避免单文件过度膨胀；拆分与否以可读与可定位为优先，不必为拆而拆。
- 测试风格：测试意图优先通过用例/方法名与必要的说明表达；避免依赖脆弱的选择器或实现细节，除非 TASK 明确要求。
- 手动验证：依赖真实浏览器、网络或后端服务的功能，须在对应 DOC_XXX.md 的验证结果章节中写明步骤与结论（含主流浏览器或指定版本）。
- TASK 为准：是否必须自动化测试、验收口径以对应 TASK_XXX.md 的验收标准为准；DOC 中的验证记录应与之一致。
